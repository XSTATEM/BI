# Справочник базы данных (для ИИ и людей)

Назначение: чтобы понять структуру Postgres-базы и бизнес-логику пайплайна не перечитывая все `.py`/`.sql` файлы заново. Читайте этот файл в начале работы вместо разбора кода с нуля.

Собран по состоянию кода на **2026-07-27** (источники: `dax_queries.py`, `pbi_to_postgres.py`, `join_marketplaces.sql`, `history.SQL`, `postgres_to_gsheets.py`). Живого доступа к самой Postgres при составлении не было — схема реконструирована из кода. Раздел «Как свериться с реальной БД» в конце — как проверить, что справочник ещё актуален.

Общее устройство пайплайна и порядок запуска — в `README.md`. Здесь — только структура данных.

## 1. Таблицы, которые перезаписываются из Power BI (`pbi_to_postgres.py`)

Каждый запуск делает `pandas.to_sql(if_exists="replace")` — таблица полностью пересоздаётся, старые данные теряются (глубина выгрузки — 90 дней, `DATESINPERIOD(..., -90, DAY)` в `dax_queries.py`). Перед перезаписью скрипт дропает зависимые вьюхи (раздел 2), после — их нужно пересоздать через `join_marketplaces.sql`.

### 1.1 `fact_revenue_wb`, `fact_revenue_ozon`, `fact_revenue_yandex`

Грейн: **одна строка = SKU + Дата**. Ключ соединения между таблицами и со справочниками — `"SKU (ключ)"` + `"Date"`. Источник — `dax_queries.py` (`raw_wb`/`raw_ozon`/`raw_yandex`), каждый маркетплейс выгружается отдельно своими реальными мерами (без DAX-заглушек под чужие колонки — объединение сделано в Postgres, не в Power BI).

**Общий FR_-блок** (выручка/затраты/остатки) — задуман как единый набор колонок по всем трём МП, но не каждая мера физически существует в модели для каждого маркетплейса (см. колонку «Есть у»):

| Колонка | Смысл | Есть у |
|---|---|---|
| `FR_Заказы, шт.` | заказано штук, ДО вычета возвратов. Переименована 03.08.2026 из `FR_Продажи, шт.` (сама мера в PBI не менялась). Соотношение: `FR_Заказы, шт.` − `FR_Возвраты, шт.` = `FR_Выкупы, шт` | WB, Ozon, Yandex |
| `FR_Возвраты, шт.` | возвраты в штуках | WB, Ozon, Yandex |
| `FR_Сумма возвратов, руб` | сумма возвратов. **У WB это не рублёвая мера возвратов** (её в модели нет), а «Себестоимость возвратов WB» — по решению пользователя, осознанное отличие от Ozon/Yandex, где это настоящая рублёвая мера | WB (=себестоимость!), Ozon, Yandex |
| `FR_Выкупы, шт` | выкупы в штуках | WB, Ozon, Yandex |
| `FR_Продажи до скидок с НДС` | выручка до скидок МП, с НДС | WB, Ozon, Yandex |
| `FR_Скидки МП` | скидка за счёт маркетплейса: WB — СПП (`Размер СПП`), Ozon — `Скидка МП, р Oz` (= «Баллы за скидки»), Yandex — `Скидки МП, руб Yam`. **Мера Yandex исправлена 03.08.2026**: её прежняя формула `[Продажи] − [Выручка по выкупам]` алгебраически схлопывалась в `[Возвраты, руб Yam]`, то есть колонка показывала возвраты, а не скидки. Теперь это сумма скидок Маркета (другие скидки Маркета + бонусы СберСпасибо + баллы Яндекс Плюс) × доставлено, Продажи − Возвраты. Цифры за прошлые периоды изменятся после перезапуска `pbi_to_postgres.py` | WB, Ozon, Yandex |
| `FR_Выручка по выкупам, руб` | выручка по факту выкупа, с НДС | WB, Ozon, Yandex |
| `FR_Комиссия` | комиссия МП. У Ozon это «Комиссия + эквайринг» одной суммой (эквайринг отдельно не выделяется) | WB, Ozon, Yandex |
| `FR_Эквайринг` | эквайринг отдельной строкой | WB, Yandex (у Ozon эквайринг не выделяется отдельно от комиссии) |
| `FR_Логистика прямая` | прямая логистика. У Ozon исходная мера хранит сумму со знаком минус — оборачивается в `ABS()` при выгрузке (`dax_queries.py`), чтобы быть положительной, как у WB | WB, Ozon (у Yandex логистика не разбита прямая/обратная) |
| `FR_Обратная и прочая логистика` | обратная логистика. У Ozon аналогично `FR_Логистика прямая` оборачивается в `ABS()` — исходная мера отрицательная | WB, Ozon |
| `FR_Прочие удержания` | штрафы/прочие удержания | WB, Ozon |
| `FR_Продвижение, руб` | расходы на продвижение/рекламу | WB, Ozon, Yandex |
| `FR_Выручка по выкупам без НДС, руб` | то же, без НДС | WB, Ozon, Yandex |
| `FR_MP Cost с НДС, руб` | суммарная стоимость услуг МП, с НДС | WB, Ozon, Yandex |
| `FR_НДС вычет на MP Cost` | вычет НДС по MP Cost | WB, Ozon, Yandex |
| `FR_Себес УУс` | себестоимость (управленческий учёт). Отдельной меры «УУс» в модели нет — используется обычная себестоимость по МП | WB, Ozon, Yandex |
| `FR_Маржа, руб` | маржа без НДС | WB, Ozon, Yandex |
| `FR_Выручка по заказам, руб` | выручка по заказам (не по выкупам) | WB, Ozon, Yandex |
| `FR_Ср. цена, руб` | средняя цена выкупа | WB, Ozon, Yandex (в raw-таблице есть, но **не** проброшена в `v_marketplaces_full`) |
| `FR_Доля себестоимости, %` | доля себестоимости в выручке | WB, Ozon, Yandex (аналогично — только в raw, не в финальной витрине) |

Колонки, которых нет у конкретного МП, при объединении в `v_marketplaces_raw_union` (раздел 2.1) становятся `NULL` — это эквивалент `BLANK()` из DAX.

**Ценовой блок** (добавлен 03.08.2026, есть у всех трёх МП — раньше `Цена в ЛК` была WB-only):

| Колонка | Смысл | Источник по МП |
|---|---|---|
| `Цена в ЛК` | базовая цена в профиле товара — то, что продавец выставил в личном кабинете, до скидок маркетплейса | WB — `[Цена в ЛК]` (`wb_prices[discounted_price]`); Ozon — `[Цена в ЛК, руб Oz]` (`ozon_daily_prices[price]`); Yandex — `[Цена в ЛК, руб Yam]` (`ya_daily_prices_lk[price_value]`, оно же `basic_price_value` профиля бизнеса) |
| `Цена на МП` | цена, которую реально видит и платит покупатель — после скидок за счёт маркетплейса | WB — `[Цена на WB]` (Выручка после СПП / Выкупы); Ozon — `[Цена на МП, руб Oz]`; Yandex — `[Цена на МП, руб Yam]` |
| `Выручка выкупов по цене в ЛК, руб` | `FR_Выкупы, шт` × `Цена в ЛК` — сколько принесли бы фактические выкупы по цене из ЛК. Разница с `FR_Выручка по выкупам, руб` = потери на скидках МП. Считается в `join_marketplaces.sql`, не в Power BI | все три МП (последняя колонка каждой ветки UNION) |

**Важные ограничения ценового блока:**
- У Ozon и Yandex `Цена в ЛК` берётся из ежедневных снимков цен (`ozon_daily_prices` / `ya_daily_prices_lk`), которые начали накапливаться **03.08.2026**. За более ранние даты колонка пустая, и `Выручка выкупов по цене в ЛК, руб` вместе с ней. Со временем история нарастёт сама.
- У WB источник `wb_prices` — снимок **без даты**, поэтому одна и та же текущая цена проставляется на все 90 дней выгрузки. Сравнивать WB и Ozon/Yandex по этой колонке в исторической динамике нельзя.
- `Цена в ЛК` у Yandex покрывает только те SKU, у которых базовая цена реально задана в профиле (на 03.08.2026 — 22 из 72 позиций каталога); у остальных работает только цена магазина.
- `Цена на МП` считается из факта транзакций, поэтому в дни без выкупов она пустая. На редких SKU в коротких периодах, где возвратов больше продаж, `FR_Выкупы, шт` уходит в минус и цена получается отрицательной — это не ошибка меры, а деление на отрицательное количество.

**Удалённое/задвоенное** (сознательные решения, см. комментарии в `join_marketplaces.sql`) — не пытаться восстанавливать без явного запроса пользователя:
- `ДРР, %` — удалена пользователем из всех трёх raw-выгрузок, колонки физически нет.
- `Остаток FBS, шт` — намеренно исключена из `fact_revenue_wb`/остальных `fact_revenue_*`: это остаток на складе продавца (FBS), её место — только в `warehouse_stocks`/`v_warehouse_stocks_fbs` (раздел 2.3), не в выручке по МП.
- `FR_Выручка без НДС, руб` — дублировала `FR_Выручка по выкупам без НДС, руб` под другим именем, физически в Postgres не попадала (баг pandas.to_sql на одинаковых данных под двумя именами) — убрана из запросов.
- `FR_Комм.маржа без НДС`, `FR_MP Cost с НДС` (без «, руб»), `FR_Себес УУс` в «коротком» варианте — дубликаты уже существующих колонок, не выводятся отдельно.
- `FR_Доля от общей выручки, %`, `FR_Доля себестоимости, %` (в финальной витрине), `FR_MP Cost, %` — убраны по просьбе пользователя из `v_marketplaces_full` (в raw-таблицах часть из них ещё может быть).

**WB-специфичные колонки** (аналитика карточки — есть только в `fact_revenue_wb`, у Ozon/Yandex `NULL` в объединённой вьюхе; `Цена в ЛК` из этого списка исключена 03.08.2026 — теперь она есть у всех трёх МП, см. «Ценовой блок» выше; колонка `Цена на WB` удалена 03.08.2026 — её позицию заняла `Цена на МП`, см. там же): `Цена базовая WB, руб`, `Акция`, `Гипотеза`, `Результат гипотезы`, `Негативы (кол-во)`, `Негативы, %`, `Рейтинг`, `Кол-во отзывов`, `Негативы (СС30)`, `CR Корзина/Заказ/Общий, %`, `Выкуп, %`, `Клики, шт`, `Корзины, шт`, `Заказы, шт`, `Продажи, шт`, `Расход РК, руб`, `Расход на отзывы, руб`, `Маржа по продажам на единицу, руб`, `ROI`, `Остаток FBO, шт` (переименована из `Остаток FBW, шт` — читай ниже), `Запас ФБО в днях продажи` (переименована из `Запас, дни`, для Ozon/Yandex такой меры нет — `NULL`).

Суффиксы у части «сырых» WB-колонок (есть в `fact_revenue_wb`, но не все доходят до `v_marketplaces_full`):
- `(СС6)` — то же самое, но за скользящий период 6 дней;
- `(СС30)` — скользящий период 30 дней;
- `(на сегодня)` — вариант меры «на сегодняшний момент», а не за весь день.

### 1.2 `dim_sku` — справочник SKU

Источник — `Справочник SKU` в модели Power BI (изначально загружается из `Справочник артикулов.xlsx`, лежит в этой же папке). Ключ — `"SKU (ключ)"`.

Колонки, используемые в `v_marketplaces_full` (раздел 2.4): `Название товара`, `Yandex SKU`, `WB Артикул`, `WB nm_id`, `Ozon Артикул`, `Ozon SKU`, `На Yandex`, `На WB`, `На Ozon` (флаги «Да/Нет» — участвует ли SKU в выгрузке по этому МП, использованы как фильтр в `dax_queries.py`), `SKU_upper`.

### 1.3 `dim_calendar` — календарь

Источник — таблица `Календарь` в модели. Ключ — `"Date"`. Колонки, используемые в `v_marketplaces_full`: `Год`, `Месяц`, `День`, `Месяц Сортировка`, `Неделя Сортировка` (ключ соединения с планом по неделям), `День Сортировка`, `Неделя (коротко)`, `Ярлык недели`.

### 1.4 `dim_plan` — план по направлениям

Источник — таблица `План` в модели, «длинный» формат: `Направление`, `Показатель`, `Неделя Сортировка`, `Значение`, `Неделя Сортировка` (совпадает по смыслу с одноимённой колонкой `dim_calendar`).

Важные особенности `Направление` в этой таблице (отличается от написания в остальных таблицах, проверено через `SELECT DISTINCT`):
- `'ВБ Ечипс'`, `'ВБ Матрасы'` → WB; `'ОЗОН ...'` → Ozon; `'Яндекс ...'` → Yandex;
- `'МВМ Ечипс'` — неизвестный маркетплейс, в `fact_revenue_*` такого нет, сознательно не матчится;
- `'общее'`, `'общее Ечипс'` — план суммарно по всем МП (см. `v_plan_total`, раздел 2.2);
- `'Ечипс'` пишется кириллицей, тогда как в остальных таблицах направление — `'Echips'` латиницей (перевод делается в `join_marketplaces.sql`).

Показателей 8, но в `v_plan_by_marketplace`/`v_plan_total` берутся только `'Выручка, план'`, `'Маржа, план'`, `'Маржа %, план'` — капитал/закупки/расходы намеренно не тянутся в витрину.

### 1.5 `transfer_items` — товары в пути (сырьё)

Источник — таблица `Transfer_items`, есть только в модели Power BI, не в исходных таблицах учётной системы. Колонка `"Дата отгрузки"` — тип `String` в модели, формат `ДД.ММ.ГГГГ` (нужен `TO_DATE(..., 'DD.MM.YYYY')`, обычный `CAST` падает). Используется только через вьюху `v_transfer_items_by_sku_warehouse` (раздел 2.3) — сама таблица напрямую не читается витринами.

### 1.6 `fact_transit_receivables` — товары в пути на МП / дебиторка авансов

Источник — `dax_queries.py` (`raw_transit_receivables`), меры из `'_МЕРЫ WAREHOUSE'` и `'_Меры ALL'`. Ключ — только `"SKU (ключ)"`, **без Даты и Маркетплейса** — сами PBI-меры считаются по SKU в целом.

Колонки: `Товаров в пути на МП, руб`, `Товаров в пути на МП, шт`, `Товаров в пути от поставщика, руб`, `Дебиторка авансы поставщикам, руб`.

⚠️ Внутри исходной PBI-меры «Сумма/Кол-во в пути, Рязанка-МП» есть фильтр `_IsLaptop` (проверка, что название товара содержит «ноутбук») — не подтверждено, осознанное ли это ограничение или старое название фильтра. Не полагаться на полноту этих 4 колонок без дополнительной проверки у пользователя.

### 1.7a `dim_cost_price` — себестоимость по SKU (добавлена 21.08.2026)

Источник — таблица `Себестоимость и товары` в модели Power BI, тянется целиком через `dax_queries.py` (`EVALUATE 'Себестоимость и товары'`). Грейн: одна строка = `Артикул поставщика` + `Месяц себестоимости` (несколько строк на SKU — по одной на каждый месяц, где себестоимость менялась).

Колонки: `Направление`, `Производитель`, `Товар`, `ВБ Номенклатура`, `ОЗОН Номенклатура ` (с пробелом в конце имени — так в источнике), `Артикул поставщика`, `для УЦ`, `Баркод`, `Размер`, `Месяц себестоимости`, `Сумма себестоимость` (⚠️ text, не numeric — см. `v_cost_per_sku`), `Копия Артикул поставщика`.

Сама по себе эта таблица не используется напрямую ни одной вьюхой/скриптом — только через `v_cost_per_sku` (раздел 2, ниже), которая сопоставляет её с `dim_sku` и выбирает актуальную цену за единицу.

⚠️ Не путать с `cost_price` — это ДРУГАЯ, отдельная M-запрос-таблица в той же модели (читает тот же исходный Google Sheet напрямую, с unpivot по месячным колонкам вида «СС 01.2026») — в Postgres не выгружается и этим пайплайном не используется.

### 1.7 `ozon_nomenclature` — справочник Ozon (⚠️ НЕ из Power BI)

Единственная таблица в этой базе, которую пишет не `pbi_to_postgres.py`, а отдельный проект `main_ozon.py`/`ozon.py` (`get_nomenclature_un`, папка `G:\script`, не `BI/`) — оба проекта используют одну и ту же Postgres-базу (`mpdb`). Полностью перезаписывается (upsert по `offer_id`+`client_id`) при каждом запуске `main_ozon.py`, независимо от расписания BI-пайплайна.

Грейн: **одна строка = offer_id + client_id** (`client_id` — id кабинета Ozon как есть, без расшифровки в название; сопоставление кабинет→название — только в `accounts.xlsx` основного проекта, в Postgres его нет).

Колонки: `offer_id`, `name`, `barcode`, `sku_fbo`, `sku_fbs` (SKU по схемам FBO/FBS из `sources`), `description_category_id`, `type_id`, `type_name`, `description_category_name`, `weight`, `weight_unit`, `width`, `height`, `depth`, `dimension_unit`, `volume_weight`, `price`, `old_price`, `premium_price`, `vat`, `is_archived`, `client_id`.

⚠️ **Себестоимости здесь нет** — Ozon её через API не отдаёт (это внутренние закупочные данные продавца, не то, что публикуется на площадке). `price`/`old_price`/`premium_price` — цена из ЛК продавца, не себестоимость.

Экспортируется в Google Sheets через `postgres_to_gsheets.py` (см. раздел 3).

## 2. Вьюхи (пересоздаются вручную, `join_marketplaces.sql` + `history.SQL`)

### 2.0 `v_cost_per_sku` — себестоимость за единицу товара (добавлена 21.08.2026, `history.SQL` раздел 4.5)

Общая для разделов 2.3 и 2.4 ниже — считает **одну цену за единицу товара на SKU** для рублёвой оценки складских остатков (запрос пользователя: "рублевый эквивалент для каждого товарного показателя по формуле Количество × Управленческая себестоимость").

Источник — `dim_cost_price` (раздел 1.7a). **Не придумана заново** — воспроизводит уже одобренную пользователем PBI-меру `Запас на FBO, руб WB/Oz` (таблица `'_МЕРЫ WAREHOUSE'`, папка "Запас FBO"):
- `dim_cost_price."Артикул поставщика"` сопоставляется с `dim_sku` по **любому** совпадению из 4 полей: `SKU_upper` (через `UPPER()`), `WB Артикул`, `Ozon Артикул`, `Yandex SKU`;
- на каждый совпавший SKU берётся строка с **самым поздним** `Месяц себестоимости`, её `Сумма себестоимость` — это и есть цена за единицу (при равенстве месяца у нескольких строк — берётся строка с максимальным значением, как `MAXX(...)` в самой PBI-мере);
- `Сумма себестоимость` в источнике — text, приводится к `numeric` через `NULLIF(...,'')::numeric`. Если `CREATE VIEW` упадёт с ошибкой приведения типа — в колонке есть нечисловой мусор, нужно почистить исходный Google Sheet.

**Отличие от PBI-меры**: там `IFERROR(VALUE(...),0)` при ошибке парсинга молча даёт 0. Здесь — `NULL`, чтобы "нет данных о себестоимости" не выглядело как "себестоимость = 0" в рублёвой колонке (на `SUM()` в Google Sheets разницы нет).

Отдаёт себестоимость под двумя ключами: `"SKU (ключ)"` (для `join_marketplaces.sql`) и `"SKU_upper"` (для `history.SQL`, где остатки идут по `nomenclatura.articul`).

⚠️ Должна пересоздаваться **до** `v_warehouse_stocks_fbs`/`v_stocks_all_total`/`v_stocks_by_marketplace`/`v_marketplaces_raw_union` — добавлена в `DEPENDENT_VIEWS` (`pbi_to_postgres.py`), порядок запуска не изменился: `pbi_to_postgres.py` → `history.SQL` → `join_marketplaces.sql`.

### 2.1 `v_marketplaces_raw_union`

`UNION ALL` трёх `fact_revenue_*` в одну таблицу (аналог `UNION` в DAX). Добавляет колонку `"Маркетплейс"` (`'WB'`/`'Ozon'`/`'Yandex'`). Колонки, которых нет у конкретного МП — `NULL`. Также здесь считается `FR_Дебиторка с НДС, руб` = `FR_Выручка по выкупам, руб − FR_MP Cost с НДС, руб`. Колонка `FR_Прочие списания, руб` — пустышка (`NULL`) во всех ветках; раньше на этом месте была расчётная `FR_Общие удержания по кабинету` (сумма Комиссии/Эквайринга/Логистики/Прочих удержаний/Продвижения), убрана по запросу пользователя.

### 2.2 `v_plan_by_marketplace`, `v_plan_total`

Разворачивают `dim_plan` из длинного формата в широкий (план выручки/маржи по неделям), с нормализацией названий направлений (см. 1.4). `v_plan_by_marketplace` — план в разрезе конкретного МП, `v_plan_total` — план суммарно по всем МП («общее»).

### 2.3 Остатки на складах (`history.SQL`)

- **`warehouse_stocks`** — исходная таблица остатков FBS (склад продавца), не создаётся этим пайплайном (внешняя система). Колонки: `nomenclatura_id`, `warehouse_id`, `quantity_instock`, `quantity_ordered`, `quantity_reserved`, `quantity_forshipment`, `quantity_total`, `created_at`.
- **`warehouse_stocks_history`** — история изменений `warehouse_stocks`, пишется триггером `trg_warehouse_stocks_history` на каждый INSERT/UPDATE/DELETE. `operation_type`: `'I'`/`'U'`/`'D'`.
- **`nomenclatura`**, **`warehouses`** — внешние справочники (не в этом репозитории). `nomenclatura.articul` = SKU (артикул), `nomenclatura.code` — внутренний код (не используется по умолчанию). `warehouses.name` = склад.
- **`v_transfer_items_by_sku_warehouse`** — товары в пути по SKU+Складу: сумма `Количество (в единицах хранения)` по всем отгрузкам с `Дата отгрузки` в скользящем окне последних 14 дней от `CURRENT_DATE` (окно пересчитывается при каждом обращении к вьюхе).
- **`v_warehouse_stocks_fbs`** (переименована из `v_warehouse_stocks_full`, т.к. это остатки именно по схеме FBS) — остаток «на конец дня» по SKU+Складу+Дате, из `warehouse_stocks_history` (последнее состояние за день, `DELETE`-записи исключены). Колонки: `Дата`, `SKU`, `Склад`, `Доступно`, `Зарезервировано`, `Отгружается`, `Всего`, `Заказано`, `В пути` (сумма за последние 14 дней из `v_transfer_items_by_sku_warehouse`, проставлена только на самую свежую дату по паре SKU+Склад). Даты бакетятся по UTC явно (`AT TIME ZONE 'UTC'`) — иначе результат зависел бы от таймзоны сессии подключения. **Добавлены 21.08.2026** (в конец, после всех «штучных» колонок; префикс `FR_` — по запросу пользователя): `FR_Доступно, руб`, `FR_Зарезервировано, руб`, `FR_Отгружается, руб`, `FR_Всего, руб`, `FR_Заказано, руб`, `FR_В пути, руб` — каждая = соответствующая колонка в штуках × `v_cost_per_sku."Себестоимость_ед, руб"` (раздел 2.0).
- **`v_stocks_all_total`** — один суммарный остаток на SKU+Дату: FBS (`Доступно`) + FBW (WB) + Ozon (`Остаток Ozon`) + Yandex (`Остаток Yandex`). Резервы (`Зарезервировано`/`Резерв Ozon`/`Резерв Yandex`) сознательно не включены — это «занятые», недоступные к продаже остатки. **Добавлена 21.08.2026**: `FR_Всего, руб` = `Всего` × себестоимость за единицу (раздел 2.0).
- **`v_stocks_by_marketplace`** — то же, но без FBS и без агрегации: одна строка на Дата+SKU+Маркетплейс. **Добавлена 21.08.2026**: `FR_Остаток, руб` = `Остаток, шт` × себестоимость за единицу (раздел 2.0).

Ключ соединения SKU между `fact_revenue_*` (`"SKU (ключ)"`) и остатками FBS (`nomenclatura.articul`) — сравнение через `UPPER(...)` (артикулы могут отличаться регистром).

### 2.4 `v_marketplaces_full` — главная витрина

`v_marketplaces_raw_union` + `dim_sku` (по `SKU (ключ)`) + `dim_calendar` (по `Date`) + `v_plan_by_marketplace`/`v_plan_total` (по Маркетплейс+Направление+Неделя) + `fact_transit_receivables` (по `SKU (ключ)` — **без** Даты/МП).

⚠️ **Фильтр по складам (только здесь)**: 6 FBS-колонок (`Доступно (FBS), шт` и т.п.) в CTE `fbs_agg` (`join_marketplaces.sql`) суммируются **только** по складам `Авито`, `Б/У запчасти`, `Блогеры`, `Брак`, `Запчасти (Челябинск)`, `Ожидает запчасти`, `Подменные ноутбуки Челябинск`, `Ремонт`, `Челябинск`, `Рязанка склад Москва` — остальные склады из `v_warehouse_stocks_fbs."Склад"` в эти колонки не попадают. Фильтр действует только в `v_marketplaces_full`; сама `v_warehouse_stocks_fbs` (лист «Остатки FBS», `daily_sales_report.py`, `telegram_bot.py`) не фильтруется и отдаёт все склады.

На складской строке (`Маркетплейс = NULL`) `Остаток (все источники), шт` считается напрямую как `Всего (FBS), шт` + (Остаток FBW+Ozon+Yandex по SKU+Дате, CTE `fbo_agg`) + `В пути (FBS), шт` — так это равенство держится по построению. Раньше `Остаток (все источники), шт` брался из `v_stocks_all_total` (history.SQL) и не сходился: та вьюха считала FBS-часть по всем складам без фильтра выше и по `Доступно`, а не `Всего`, и вообще не учитывала `В пути`. `v_stocks_all_total`/`v_stocks_by_marketplace` (лист «Все остатки»/«Остатки МП») этой правки не касаются.

⚠️ Сама колонка `Остаток FBO, шт` на складской строке остаётся `NULL` — суммарный FBW+Ozon+Yandex туда сознательно не выводится, потому что те же числа по отдельности уже есть на WB/Ozon/Yandex-строках того же SKU в этой же колонке. Если бы сумму вывели и там, простой `SUM()` по столбцу «Остаток FBO» в Google Sheets задваивал бы FBW/Ozon/Yandex-остатки (WB/Ozon/Yandex-строки + складская строка) — это и наблюдалось на практике (Направление=Echips, 08.08: `Всего FBS + Остаток FBO + В пути FBS` не сходилось с `Остаток (все источники)` ровно на задвоенный FBO).

⚠️ **Из-за джойна `fact_transit_receivables` только по SKU**, 4 колонки (`Товаров в пути на МП, руб/шт`, `Товаров в пути от поставщика, руб`, `Дебиторка авансы поставщикам, руб`) **одинаковы на каждой строке SKU** независимо от даты и маркетплейса. Суммировать их по датам/МП в сводной таблице/Google Sheets **нельзя** — сумма задвоится/затроится. Для корректного итога по SKU нужно брать значение из одной строки (MIN/MAX/любая одна), а не `SUM()` по всем.

**Добавлены 21.08.2026** (в конец `v_marketplaces_raw_union`, то есть перед всей «технической» частью выше — dim_sku/dim_calendar/план/transit; префикс `FR_` — по запросу пользователя, как у остальных колонок общего FR_-блока): `FR_Остаток FBO, руб`, `FR_Доступно (FBS), руб`, `FR_Зарезервировано (FBS), руб`, `FR_Отгружается (FBS), руб`, `FR_Всего (FBS), руб`, `FR_Заказано (FBS), руб`, `FR_В пути (FBS), руб`, `FR_Остаток (все источники), руб` — каждая = соответствующая колонка в штуках × `v_cost_per_sku."Себестоимость_ед, руб"` (раздел 2.0). Как и их «штучные» аналоги: `FR_Остаток FBO, руб` заполнена только на строках WB/Ozon/Yandex (`NULL` на складской строке), остальные 7 — только на складской строке (`NULL` на WB/Ozon/Yandex).

Это финальная витрина, которую читают `postgres_to_gsheets.py` (лист `v_marketplaces_full`), `daily_sales_report.py` и `telegram_bot.py`.

## 4. Глоссарий терминов

| Термин | Значение |
|---|---|
| **FBO / FBW** | Fulfillment by Operator/Wildberries — товар хранится и отгружается со склада маркетплейса |
| **FBS** | Fulfillment by Seller — товар хранится и отгружается со склада продавца |
| **МП** | маркетплейс (WB / Ozon / Yandex) |
| **ДРР** | доля рекламных расходов (мера удалена из базы, см. 1.1) |
| **MP Cost** | суммарная стоимость услуг маркетплейса (комиссия+логистика+эквайринг и т.п.) |
| **СПП** | скидка постоянного покупателя (WB) — здесь используется как `FR_Скидки МП` |
| **СС6 / СС30** | скользящий период 6 / 30 дней |
| **Направление** | бренд/товарное направление (Echips, Digma, Аксы, Матрасы, Безикейность и т.п.) |
| **Грейн** | уровень детализации строки таблицы (например «SKU + Дата») |

## 5. Как свериться с реальной БД

Прямого доступа к живой Postgres при составлении справочника не было (креды берутся из переменных окружения, нигде не хранятся в репозитории — см. `README.md`). Если нужно проверить, что справочник ещё соответствует реальности, выполните в `psql` (или через любой SQL-клиент с доступом к базе):

```sql
-- Список таблиц и вьюх в схеме
SELECT table_name, table_type
FROM information_schema.tables
WHERE table_schema = 'public'
ORDER BY table_type, table_name;

-- Колонки конкретной таблицы/вьюхи (пример)
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'fact_revenue_wb'
ORDER BY ordinal_position;
```

Если результат разошёлся с этим файлом (появились/пропали таблицы или колонки) — актуализируйте `DATA_DICTIONARY.md`, а не только код: этот файл читается в начале работы вместо разбора `.py`/`.sql`.
